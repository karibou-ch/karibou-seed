# **KARIBOU — SCHÉMA UX GLOBAL**

### **Services · Marchés · Temps · Publics**

Karibou est un marché unifié, structuré par le temps, où les sous-marchés deviennent visibles ou non selon le jour de livraison choisi.

---

**Règle de lecture**

* **(structurant)** = si on se trompe ici, tout le reste devient bancal
* **(à surveiller)** = juste, mais peut évoluer / s'ajuster en cours de route
* **(secondaire)** = important, mais ne doit jamais bloquer le chantier

## **🟢 1. INTENTION CLIENT — (structurant)**

Le client qui arrive sur karibou.ch a une **intention** qu'il faut identifier et résoudre avec l'UX.

### **1.1 Les 4 intentions fondamentales**

| Intention | Description | Discriminant | Page cible |
|-----------|-------------|--------------|------------|
| **Faire mes courses** | Commande ponctuelle, explorer le marché | Client standard | `/home` (marché) |
| **Recevoir un buffet** | Valoriser un événement avec les artisans | Nombre de personnes, date | `/buffet` |
| **Ne plus oublier** | Commande automatique récurrente | Produits de base réguliers | `/subscriptions` |
| **Besoin d'aide** | Questions, conseil, accompagnement | Incertitude, question | `/assistant` (James) |

### **1.2 Détail des intentions**

#### 🛒 **Faire mes courses** (Commande ponctuelle)
- **Qui** : Tout client (nouveau ou régulier)
- **Besoin** : Explorer l'offre, choisir des produits, commander pour une date
- **Parcours** : `/home` → catégories → produits → panier → checkout
- **Variante** : Peut aussi explorer avec James (conversation + suggestions)
- **Discriminant** : Pas de nombre de personnes, pas de date lointaine

#### 🎉 **Recevoir un buffet** (Événement artisanal)
- **Qui** : Particuliers ET professionnels (≠ ancienne page "B2B")
- **Besoin** : Valoriser un événement avec les produits des artisans genevois
- **Parcours** : `/buffet` → kits → configurateur → devis (si J+6) ou commande
- **Discriminants** :
  - "Pour combien de personnes ?" (10, 50, 100+)
  - "Pour quelle date ?" (si > J+6 → devis)
- **Note historique** : Premiers clients = particuliers, pas entreprises. Le terme "B2B" était une erreur de positionnement.

#### 🔄 **Ne plus oublier** (Commande automatique)
- **Qui** : Client régulier qui veut simplifier
- **Besoin** : Automatiser les produits de base (fruits, légumes, pain, œufs...)
- **Parcours** : `/subscriptions` → produits éligibles → configuration fréquence/jour
- **Discriminant** : "J'en ai besoin chaque semaine"
- **⚠️ Clarification importante** : Ce n'est PAS un abonnement contraignant, c'est un **service pour ne pas oublier**. Pas de contrainte, pas d'engagement.

#### 💬 **Besoin d'aide** (Accompagnement James)
- **Qui** : Client qui a une question ou besoin de conseil
- **Besoin** : Être guidé, poser une question, obtenir des suggestions
- **Parcours** : `/assistant/james` → sélection de questions OU conversation libre
- **Présentation** : Sélection de questions types + champ libre
- **Aide contextualisée** : Une fois le besoin identifié, James s'adapte au contexte

### **1.4 Principe clé : Consulter ≠ Commander**

⇒ **Consulter** = explorer librement, comprendre l'offre (sans date obligatoire)
⇒ **Commander** = valider un achat (date requise)
⇒ La règle "je choisis un jour" devient pertinente au moment de valider, pas avant

### **1.5 Problèmes résolus par cette approche**

| Problème | Impact | Solution |
|----------|--------|----------|
| À quel moment choisir la date ? | Friction en exploration | Date = point de validation, pas d'entrée |
| Comment différencier les offres ? | Confusion services | Aiguillage par intention (4 choix clairs) |
| Limite J+6 pour buffets > 1 mois | Blocage devis | Mode devis automatique si date > J+6 |
| "B2B" mal compris | Exclusion particuliers | Renommer en "Buffet" (tous publics) |
| "Abonnement" = contrainte | Perception négative | Renommer "Ne plus oublier" (service) |

## **🟣 1bis. AIDE CONTEXTUALISÉE (James) — (structurant)**

**Une fois le besoin identifié, l'aide s'adapte au contexte du client.**

### **Principe fondamental : Assistant Neutre vs Encadré**

James existe sous **deux formes** complémentaires :

| Mode | Localisation | Comportement |
|------|--------------|--------------|
| **NEUTRE** | `/assistant` (page dédiée) | Toutes les questions possibles, pas de contexte prédéfini |
| **ENCADRÉ** | Widget dans `/home`, `/buffet`, `/subscriptions` | Questions filtrées selon le domaine, contexte automatique |

**Assistant NEUTRE (`/assistant`)** :
- Sélection de questions types couvrant TOUS les domaines
- Conversation libre sans restriction
- Création panier vocal
- Redirection contextuelle après identification du besoin

**Assistant ENCADRÉ (dans les pages domaines)** :
- Dans `/home` (courses) → suggestions produits, recettes
- Dans `/buffet` → aide au configurateur, estimation quantités
- Dans `/subscriptions` → conseil fréquence, produits complémentaires
- Dans `/cart` → vérification commande

## **🟡 2. COUCHE TEMPS — (structurant)**

**Intention** (côté client)

- pouvoir explorer l'offre librement, sans contrainte immédiate
- comprendre ce qui est disponible et à quel moment
- acheter maintenant **ou** se projeter plus tard (événement, devis, abo)
- ne pas se heurter à une règle bancaire ou technique incomprise

👉 *« Je veux voir ce que vous proposez, et comprendre **quand** je peux commander. »*

**Problèmes**

- La contrainte J+6 max est technique (pré-autorisation bancaire) - non intuitive pour le client
- Aujourd'hui : le temps est implicite / les règles ne sont pas lisibles / la différence entre consulter et commander n'est pas toujours claire
- Risque UX : frustration ("pourquoi je ne peux pas commander ?") / contournements (tests de dates, retours arrière)
- Cas buffets : besoin de se projeter à J+14 / J+30 / consultation ≠ paiement ≠ livraison

👉 Problème clé : le système sait quand on peut agir, le client non.

**Solutions**

| Horizon | Mode | Action |
|---------|------|--------|
| J+0 à J+6 | Commande directe | Pré-autorisation CB, checkout standard |
| > J+6 | Mode devis | Consultation libre, devis, pré-paiement kits |
| Récurrent | Commande auto | Configuration sans date fixe |

```
┌───────────────────────────────┐
│ Consultation libre (tous)    │
│  → produits · kits · idées   │
└───────────────────────────────┘
                │
┌───────────────────────────────┐
│ Commande possible            │
│  → J+0 à J+6                 │
│  (pré-autorisation bancaire) │
└───────────────────────────────┘
                │
┌───────────────────────────────┐
│ Au-delà de J+6               │
│  → consultation / devis      │
│  → pré-paid (kits buffet)    │
└───────────────────────────────┘
```

## **🔵 3. MARCHÉ RACINE / FAÇADE — (structurant)**

**Marchés de Genève constitue le parcours principal.**
**Les bascules (HDR, Superlocal) sont des parcours alternatifs activés par le contexte.**

**Intention**

* Accéder à **une offre unifiée** des marchés genevois
* Comprendre rapidement **ce qu'est Karibou** : des artisans / des marchés / ancrés à Genève
* Faire ses courses **sans avoir à connaître la structure interne** : marché de quartier / halle / ferme / magasin spécialisé

👉 *« Je fais mes courses sur les marchés de Genève, simplement. »*

**Problèmes**

* **Marchés de Genève** joue un double rôle : façade principale Karibou / marché réel (marchés de la Ville)
* Ce double statut peut créer des incompréhensions (est-ce un marché parmi d'autres ?) / des attentes erronées sur les jours d'ouverture
* L'ouverture volontairement limitée (mar · mer · ven) est cohérente métier / mais **non évidente pour le client : le rythme des marchés physiques (hebdomadaire) n'est pas un réflexe e-commerce.**

👉 La cohérence d'expérience prime sur l'exhaustivité, mais cette règle n'est pas lisible en tant que telle.

**Pistes de solution**

* Traiter **Marchés de Genève comme le point d'entrée par défaut**, pas comme un marché "au même niveau" que les autres
* Assumer pleinement son rôle de : **façade + marché racine**
* Faire comprendre implicitement que : l'ouverture dépend de l'offre primeurs
* Prévoir des **chemins alternatifs clairs** quand le marché racine est fermé : bascule vers Halle de Rive / bascule vers Superlocal (selon le public)

*Note* : éviter toute exposition directe de la logique interne des sous-marchés.
👉 Principe directeur : Marchés de Genève est la porte d'entrée unique ; les autres marchés sont des contextes, pas des destinations par défaut.

```
┌────────────────────────────────────────────┐
│            MARCHÉS DE GENÈVE               │
│  (marché racine + façade Karibou)          │
│  Promesse : artisans · marchés · Genève    │
└────────────────────────────────────────────┘
```

### **Ouverture volontaire**

OUVERT : mar · mer · ven
FERMÉ  : lun · jeu

Choix UX assumé : **l'offre primeurs des marchés de la Ville donne le ton**.

## **🟣 4. STRUCTURE DES SOUS-MARCHÉS — (à surveiller)**

**Intention**

* Accéder à une **offre riche et cohérente**, issue de différents lieux
* Bénéficier de la **diversité des marchés genevois**
* Sans avoir à comprendre : les statuts des lieux / leur organisation / leurs contraintes respectives

👉 *« Je profite des marchés genevois, peu importe d'où viennent exactement les produits. »* (sauf pour HDR le client cherche la marque)

**Problèmes**

* Les sous-marchés sont réels et très différents (halle, ferme, magasin, marchés de quartier), mais **présentés de manière homogène.**
  L'homogénéité n'est pas le problème ; le problème, c'est l'absence de signal au moment où la différence devient bloquante. Par ex. quand Marchés de Genève = fermé et Halle de Rive = ouvert, le basculement peut paraître arbitraire, le client a l'impression de "changer de site" ou de "perdre des produits".
* Leur existence est nécessaire côté métier mais **parasite la lecture UX** si elle est trop visible
* Risque : surcharge cognitive / mauvaise compréhension des jours d'ouverture / confusion entre "marché", "lieu", "commerçant"

👉 Problème clé : la structure interne est indispensable, mais elle n'est pas une information utile en phase d'achat.

**Solution**

* Considérer les sous-marchés comme : une **organisation interne** et un **levier de disponibilité**
* Les rendre visibles uniquement quand ils expliquent une disponibilité ou une indisponibilité
* Déporter leur rôle narratif vers storytelling / pages éditoriales / nos partenaires

👉 Principe directeur : Les sous-marchés structurent l'offre, mais ne structurent pas le parcours client.

```
MARCHÉS DE GENÈVE
├─ Marchés de la Ville de Genève
│  • marchés hebdomadaires de quartier
│  • artisans & commerçants de détail
│  • fruits & légumes = offre socle
│
├─ Halle de Rive
│  • marché couvert
│  • artisans haut de gamme de la Halle
│  • fruits & légumes possibles lun→ven
│
├─ Ferme de Budé
│  • ferme bio + marché couvert
│  • producteur & confection paniers
│
└─ Les Cuvées du Terroir
   • magasin de vente au détail
   • ambassadeur des vignerons genevois
```

👉 Tous ces sous-marchés vivent sous la bannière "Marchés de Genève".

## **🔁 5. BASCULES DE CONTEXTE (UX latérale) — (structurant)**

**Un même produit ou service peut exister dans plusieurs états (consultable, commandable, sur devis), selon le jour, le public et le contexte de marché.**

**Intention**

* Pouvoir commander même quand le marché principal est fermé / accéder à une offre adaptée à son contexte (école, semaine, contrainte)
* Comprendre rapidement pourquoi certaines offres changent, sans avoir l'impression de "changer de site"

👉 *« Je reste sur Karibou, mais le contexte s'adapte. »*

**Problèmes**

* Les bascules (Halle / Superlocal) : existent mais sont peu visibles et peu explicites
* Risque : sentiment de perte de repères / incompréhension ("où suis-je ?")
* Complexité : mêmes produits, règles différentes selon le jour et le public (ex. le pain de Bretzel est non commandable lun/jeu sur Marchés de Genève mais commandable sur Superlocal)

👉 Problème clé : Le changement de contexte n'est pas explicité comme tel.

**Pistes de solution**

* Traiter les bascules comme : un **changement de contexte** / pas comme un changement de plateforme
* Les activer : quand le marché racine est fermé / ou quand le profil client le nécessite
* Donner des signaux clairs : "vous consultez l'offre de…" / "offre adaptée à…"

Principe directeur : On ne change pas de site, on change de contexte de disponibilité.

```
┌────────────────────┐      ┌──────────────────────┐
│    HALLE DE RIVE   │      │   SUPERLOCAL         │
│  (bascule marché)  │      │  (écoles & coll.)    │
└────────────────────┘      └──────────────────────┘
```

### **Halle de Rive**

* lun → ven
* offre continue
* fruits & légumes possibles tous les jours

### **Superlocal**

* lun → ven
* offre simplifiée & adaptée
* fruits & légumes : mar · mer · ven
* primeur Halle volontairement exclu

Ces bascules : **ne changent pas la plateforme** / changent **le contexte de disponibilité**

## **🟠 6. SERVICES TRANSVERSAUX (au-dessus des marchés) — (à surveiller)**

**Intention**

* Accéder facilement à : des paniers / des commandes automatiques / des buffets événementiels / du last minute
* Sans se demander : de quel marché dépend le service / quels commerçants sont derrière

👉 *« Je choisis un service, pas un marché. »*

**Problèmes**

* Les services traversent plusieurs marchés mais peuvent apparaître rattachés à un contexte particulier. Par ex. last minute est un mode de disponibilité, pas un marché. Mais s'il est affiché uniquement certains jours, risque : confusion sur leur disponibilité / incompréhension des règles (délai, jour, public)

👉 Problème clé : Les services sont transversaux, mais leur logique n'est pas toujours lisible.

**Solution**

* Positionner les services comme une **couche au-dessus des marchés**
* Clarifier que leur disponibilité dépend : du temps / du public / de la logistique
* Traiter le last minute comme : un **état de disponibilité**, pas comme un marché ou une catégorie

👉 Principe directeur : Les services organisent l'usage, les marchés organisent l'offre.

```
┌─────────────────────────────────────────┐
│            SERVICES KARIBOU             │
├─────────────────────────────────────────┤
│ • Commandes ponctuelles (courses)       │
│ • Commandes automatiques (ne pas        │
│   oublier)                              │
│ • Buffets événementiels (tous publics)  │
│ • Last Minute (jour même)               │
│   → flag de disponibilité               │
└─────────────────────────────────────────┘
```

## **🔴 7. COUCHE CACHÉE — RÈGLES MÉTIER — (secondaire)**

**Intention**

* Pouvoir commander simplement
* Comprendre : ce qui est possible / ce qui ne l'est pas
* Sans être confronté à des contraintes techniques

👉 *« Si ce n'est pas possible, je veux une alternative claire. »*

**Problèmes**

* Les règles métier sont nombreuses :
  * paiement en 2 étapes
  * ajustement au poids
  * délais spécifiques
  * horaires / surcoûts
  * exceptions saisonnières
* Elles sont : essentielles au fonctionnement mais **incompréhensibles pour le client**
* Risque : blocages / frustration / incompréhension de la valeur du service

👉 Problème clé : Ce qui est critique pour le système ne doit jamais être central pour l'UX.

**Solution**

* Garder ces règles : invisibles par défaut / explicites uniquement quand elles impactent une action
* Toujours proposer : une alternative / un chemin de sortie (devis, autre jour, autre service)
* Éviter toute exposition directe : bancaire / logistique / contractuelle

👉 Principe directeur : **Les règles métier doivent contraindre le système, pas l'expérience client.**

```
• Pré-autorisation CB (2-step payment)
• Ajustement au poids
• Horaires de livraison & surcoûts
• Délais spécifiques (Budé, boulangerie)
• Exception saisonnière (samedi décembre)
```

**⚠️ Jamais des points d'entrée UX.**

### **8.4 Niveau 3 : Opérationnel**

**Navigation séparée** - jamais mélangée avec les services :

| Zone | Contenu |
|------|---------|
| **Compte** (drawer/modal) | Profil, Commandes, Factures, Adresses, Paiements |
| **Panier** (page dédiée) | Items courses + buffet, Checkout |

### **8.5 Panier - Clarification**

| Service | Panier | Comportement |
|---------|--------|--------------|
| **Hub** | ❌ Non | Page d'aiguillage uniquement |
| **Home** | ✅ Oui | Ajout produits → /cart/default |
| **Buffet** | ✅ Oui (click-buy) | Kits → /cart/default → checkout |
| **Subscriptions** | ❌ Non | **Contrats** (pas un panier) |
| **Assistant** | ✅ Oui | Création panier vocal → /cart/default |

**⚠️ Subscriptions = Contrats, pas panier**

Un contrat = "Chaque vendredi, livrez-moi X, Y, Z à l'adresse A"
- Pas de validation type "panier"
- Configuration récurrence + produits + adresse
- Modifiable/pausable à tout moment

### **8.6 Side Info Actions (Panel Right)**

**Variable dynamique** - liens contextuels selon l'état :

```typescript
// Exemples d'actions contextuelles
[
  { label: "Besoin d'aide ?", route: "/assistant", type: "help" },
  { label: "Votre commande de mardi", route: "/me/orders/123", type: "order", urgency: "high" },
  { label: "Panier : 3 articles", route: "/cart", type: "cart", badge: "45 CHF" }
]
```

### **8.7 Mobile : Bottom Bar + Swipe**

**Le modèle 3 colonnes avec swipe suffit.**

Le bottom bar mobile est un **raccourci vers les panels** + accès panier :

```html
<!-- Modèle kng-home -->
<nav class="mobile-appbar">
  <button (click)="scrollToPanel(0)">Menu</button>      <!-- Panel Side -->
  <button (click)="scrollToPanel(1)">Produits</button>  <!-- Panel Center -->
  <button (click)="scrollToPanel(2)">Aide</button>      <!-- Panel Right -->
  <button [routerLink]="cart">Panier</button>           <!-- Page dédiée -->
</nav>
```

**Pas de duplication des services** dans le bottom bar - chaque service a son propre bottom bar contextuel.
